## ⚠️ Python 3.11 required (do not use 3.14)
On Python 3.14 the `scipy` cp314 wheel is blocked by this machine's WDAC code-integrity policy
(`Policy ID {0283ac0f-…}`, "did not meet the Enterprise signing level requirements"), which breaks
`scipy → sklearn → sentence-transformers → app.ml.embedder` and therefore the entire app import.
Rebuilding the venv on **Python 3.11.9** resolves it (scipy drops to 1.17.1, an established build that
clears the reputation check). 3.11 also matches `backend/Dockerfile` and Render's runtime.
```
winget install Python.Python.3.11
cd backend; Remove-Item -Recurse -Force venv; py -3.11 -m venv venv
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

## ⚠️ Groq model changed — llama-3.3-70b-versatile is GONE
Groq no longer serves `llama-3.3-70b-versatile` (404 `model_not_found`). Available chat models on our key:
`openai/gpt-oss-120b`, `openai/gpt-oss-20b`, `qwen/qwen3.8-27b`, `qwen/qwen3.6-27b`, `groq/compound*`.
We now use **`openai/gpt-oss-120b`**, set once in `config.py` as `settings.GROQ_MODEL` and overridable via
`GROQ_MODEL` in `.env` — change it in that one place if Groq retires it too.
**These are reasoning models:** chain-of-thought is billed against `max_tokens` *before* any answer, so a
tight budget returns an empty `content` (this silently produced blank explanations until fixed). All calls
now pass `reasoning_effort="low"` with generous `max_tokens`, and coalesce `content or ""`.

## Round 11 — 🚨 LIVE OUTAGE: /api/paths/generate failing 100% of the time on Bedrock — found + fixed
Right after Round 10 deployed, a routine post-deploy log check turned up a real, active incident, not a hypothetical: **every one of the last 4 real users** (distinct external IPs) who reached "Generate My Path" got a hard `500` (`botocore.errorfactory.ThrottlingException: reached max retries: 4`). This is the single most important flow in the app — onboarding is unusable while this is happening.

**Root cause**: `path_service.generate_path()` fired **9 sequential Bedrock Converse calls back-to-back** for a typical path — 1 sequencing call + one `generate_explanation()` call per course (8 courses). That rapid-fire burst alone was enough to trip this AWS account's on-demand throughput quota for Meta Llama 3 70B, independent of any other traffic. `feedback_service._regenerate_tail()` (the "rebuild remaining path" escape hatch) had the identical N-calls-in-a-loop pattern.

**Asked the user**: revert the live default back to Groq (zero-risk, already proven reliable all session) vs. keep pushing on Bedrock. **Decision: keep using AWS Bedrock** — so the fix had to make Bedrock itself resilient, not route around it.

**Fixed, two layers**:
1. **Cut the call count from 9 to 2 per path generation.** New `path_service.generate_explanations_batch()` (+ new prompt `prompts/explain_batch.txt`) sends every course in the path to the LLM in ONE call and gets back a JSON object of `{course_id: explanation}` instead of one call per course. `generate_path()` now does: 1 sequencing call + 1 batch-explain call = 2 total, regardless of how many courses are in the path. Applied the identical fix to `feedback_service._regenerate_tail()` (imports and reuses the same `generate_explanations_batch()` rather than duplicating it). **Never fabricates**: any course id the batch response is missing/invalid for falls back to a real individual `generate_explanation()` call for just that one course — a partially-bad batch response still ends in every step having a real LLM-generated explanation, just slower for the few that needed the fallback.
2. **Adaptive retry mode on the Bedrock client itself** (`llm_client._get_bedrock_runtime()`): `Config(retries={"max_attempts": 8, "mode": "adaptive"})` — AWS's own recommended mitigation for `ThrottlingException`, client-side rate-limits based on observed throttling instead of just blindly retrying 3 times (boto3's default) and giving up.
- **Tested**: batch-explain function verified locally against real Groq output (3 real, distinct, correctly-keyed explanations, nothing fabricated) before deploying. Deployed to EC2 (disk checked first: 30% used, 20GB free) and re-verified `/health` after.
- **This is a mitigation, not the durable fix.** The underlying AWS Bedrock on-demand throughput quota for this model/account is still low — fewer calls + better client-side backoff makes it much more likely to succeed, but the real fix is requesting a Service Quotas increase for Bedrock (AWS Console → Service Quotas → Amazon Bedrock → find the Llama 3 70B Instruct on-demand throughput quota → request increase). I don't have console access to do this myself. **Action needed from whoever owns the AWS account.**
