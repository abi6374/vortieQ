## ⚠️ Python 3.11 required (do not use 3.14)
On Python 3.14 the `scipy` cp314 wheel is blocked by this machine's WDAC code-integrity policy
(`Policy ID {0283ac0f-…}`, "did not meet the Enterprise signing level requirements"), which breaks
`scipy → sklearn → sentence-transformers → app.ml.embedder` and therefore the entire app import.
Rebuilding the venv on **Python 3.11.9** resolves it (scipy drops to 1.17.1, an established build that
clears the reputation check). 3.11 also matches `backend/Dockerfile` and Render's runtime.
```
winget install Python.Python.3.11
cd backend; Remove-Item -Recurse -Force venv; py -3.11 -m venv venv
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

## ⚠️ Groq model changed — llama-3.3-70b-versatile is GONE
Groq no longer serves `llama-3.3-70b-versatile` (404 `model_not_found`). Available chat models on our key:
`openai/gpt-oss-120b`, `openai/gpt-oss-20b`, `qwen/qwen3.8-27b`, `qwen/qwen3.6-27b`, `groq/compound*`.
We now use **`openai/gpt-oss-120b`**, set once in `config.py` as `settings.GROQ_MODEL` and overridable via
`GROQ_MODEL` in `.env` — change it in that one place if Groq retires it too.
**These are reasoning models:** chain-of-thought is billed against `max_tokens` *before* any answer, so a
tight budget returns an empty `content` (this silently produced blank explanations until fixed). All calls
now pass `reasoning_effort="low"` with generous `max_tokens`, and coalesce `content or ""`.

## Round 9 — "sign in/sign up takes too long" — ROOT CAUSE FOUND, not a code bug
User report: sign in and sign up are slow on the live site. Investigated the whole path (AuthCard/AuthContext/apiClient — all clean, no extra blocking calls) and then tested Supabase itself directly with `curl` against the real project (`omnhtvxuvjnimokwqtje.supabase.co`), bypassing the frontend entirely:
- `GET /rest/v1/` (PostgREST/DB) → responds in ~90ms. `GET /auth/v1/health` → responds in ~150ms. `OPTIONS /auth/v1/token` (edge-handled preflight) → responds in ~110ms.
- `POST /auth/v1/token?grant_type=password` (actual sign-in), `POST /auth/v1/signup` (actual sign-up), and even `GET /auth/v1/settings` (a static config read, no password hashing involved) → **all three hang completely, 0 bytes received, until the client times out** (reproduced at 15s, 30s, and 90s timeouts — never got a response).
- **Conclusion**: the Auth (GoTrue) microservice for this specific Supabase project is hung/unresponsive for real auth operations, while the edge health-check, PostgREST, and the database are all fine. This is why sign-in/sign-up "take too long" — the request isn't slow, it's genuinely stuck until the browser's own connection timeout, since neither the Supabase JS client nor our `supabaseClient.js` sets an explicit fetch timeout.
- **Checked Supabase's public status page** (status.supabase.com): no active global incident for Auth right now, but there IS an unresolved incident as of Aug 27, 2026 — "401 errors due to JWT rejections" (PostgREST/JWT-related, hit `ap-south-1` among other regions, described as "limited to a subset of new projects"). Supabase's own latest update says **"restarting their project after the rollout resolved this issue" for some customers** who hit related symptoms.
- **This is NOT fixable by editing this repo's code** — no service/frontend/backend call is at fault; the identity provider itself isn't responding. **Action needed from whoever owns the Supabase project (dashboard access required, which I don't have — the MCP connector needs OAuth re-auth)**: go to the Supabase dashboard → Project Settings → General → **Restart project**, then re-test sign-in. If that doesn't clear it, open a support ticket referencing the "401 errors due to JWT rejections" incident, since this project may be one of the affected ones.
- **Related latent risk noticed along the way** (not the cause of this, but worth knowing): `backend/app/middleware/auth.py`'s JWT verification has a 3-tier fallback, and tier 3 (`_try_supabase_server`, calls `supabase_client.auth.get_user(token)`) hits this exact same Auth service. It's normally never reached (this project's tokens are legacy HS256, verified locally in tier 1, no network call) — but if it ever were reached while Auth is in this state, that backend request would hang too. No code change made for this since it's not currently in the failure path and touching auth fallback logic without being able to test against a healthy Auth service is riskier than leaving it.
